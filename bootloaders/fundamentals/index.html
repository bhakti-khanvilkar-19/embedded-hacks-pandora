Bootloaders

Fundamentals

What runs before an operating system exists to run anything at all — and why that job is usually split across multiple stages instead of being one program.

Why boot in stages?

At power-on, RAM is typically not yet initialized (DDR training takes real configuration work) and the only memory guaranteed to be usable is a small amount of on-chip SRAM or boot ROM. A full bootloader like U-Boot is too large to fit in that small space. So boot is split:

StageRuns fromJob
ROM code (BootROM)On-chip mask ROM, fixed at manufactureMinimal — read a boot device (eMMC, SD, SPI flash) per boot-mode pins, load the next stage into on-chip SRAM, jump to it.
SPL / TPL (Secondary/Tertiary Program Loader)On-chip SRAMInitialize DRAM controller and minimal clocking, then load the next stage into DRAM.
Full bootloader (e.g. U-Boot proper)DRAMFull driver set, storage/network access, environment variables, boot menu logic, final load of the OS kernel.
OS kernelDRAMTakes over entirely — see Linux → Boot.

Not every platform has all of these stages — a simple microcontroller typically jumps straight from a tiny ROM bootloader (or none at all) into the application. The staged model above is most visible on application-class SoCs that run Linux.

What a boot ROM actually decides

Boot-mode selection is usually determined by hardware strap pins or eFuses read very early — which storage device to read the next stage from (SD card, eMMC, SPI NOR/NAND, UART/USB recovery mode). This is why "hold this pin, it boots from USB instead" exists on many dev boards — it's a boot ROM feature, before any user code has run.

Secure/verified boot, briefly

On SoCs with a hardware root of trust, the boot ROM (or SPL) can verify a cryptographic signature on the next stage before jumping to it, forming a chain of trust — each stage verifies the next before handing off control. Skipping or misconfiguring any link in that chain breaks the guarantee for every stage after it.

What I learned

"Bricked" after a bad bootloader flash usually still isn't unrecoverable — the boot ROM stage is typically burned in mask ROM and can't be overwritten, and often supports a recovery/download mode specifically for this situation. Knowing your SoC's recovery boot mode before you need it saves a lot of stress later.
