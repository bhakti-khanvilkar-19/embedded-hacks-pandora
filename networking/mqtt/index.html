MQTT — Message Queuing Telemetry Transport

A lightweight publish/subscribe messaging protocol built on top of TCP. Instead of one device talking directly to another, every device talks to a central broker — publishers send messages tagged with a topic, and the broker fans each one out to whoever subscribed to that topic, with no publisher ever needing to know who (or how many) is listening.

The pub/sub model

This decoupling is the whole point: a publisher doesn't need to know how many subscribers exist, whether they're online right now, or where they are — it just publishes. New subscribers can appear later and start receiving without the publisher changing anything.

Topics and wildcards

A topic is a slash-separated hierarchy the application defines itself — there's no fixed schema, e.g. factory/line1/press3/temperature. Subscribers can match a specific topic exactly, or use wildcards:

+
Matches exactly one topic level. factory/+/press3/temperature matches any line.
#
Matches any number of remaining levels — must be the last character. factory/line1/# matches everything under line1.

Quality of Service: 0, 1, 2

Unlike CoAP's binary confirmable/non-confirmable choice, MQTT has three delivery guarantees, chosen per-message by the publisher:

QoSGuaranteeMechanism
0At most onceFire-and-forget — no acknowledgement, message may be lost, never duplicated.
1At least onceSender keeps retrying until it gets a PUBACK — message will arrive, but a lost ACK can cause a duplicate delivery.
2Exactly onceA four-packet handshake (PUBLISH → PUBREC → PUBREL → PUBCOMP) that both guarantees delivery and de-duplicates — the most expensive, reserved for messages where duplicates would actually cause harm (e.g. "charge this transaction").

Note QoS is between each client and the broker independently — a publisher can send at QoS 2 while a given subscriber receives at whatever QoS it subscribed with, whichever is lower wins for that hop.

Retained messages

A publisher can mark a message retained; the broker keeps the latest retained message on that topic and immediately sends it to any client that subscribes later — without waiting for the next publish. This is how a newly-connected dashboard immediately shows "last known temperature" instead of a blank value until the next reading arrives.

Last Will and Testament

When connecting, a client can register a will message with the broker — a topic and payload the broker will publish on the client's behalf if that client disconnects ungracefully (network drop, crash, power loss) rather than sending a clean DISCONNECT. This is the standard way to get reliable "device went offline" notifications without polling — a dashboard subscribes to devices/+/status and finds out immediately, from the broker, when a device vanishes.

The packet types, briefly

PacketPurpose
CONNECT / CONNACKClient authenticates and opens a session with the broker.
PUBLISHSend a message on a topic, at a chosen QoS.
SUBSCRIBE / SUBACKRegister interest in a topic (filter), broker confirms the granted QoS.
PINGREQ / PINGRESPKeepalive — lets the broker detect a dead connection before the TCP stack would.
DISCONNECTClean shutdown — explicitly tells the broker not to fire the will message.

Gotchas

Field notes
  • QoS 1 will occasionally deliver duplicates — if the application isn't idempotent to duplicate messages, QoS 1 alone doesn't save it.
  • A broker is a single point of failure and a piece of infrastructure a raw-socket or CoAP design doesn't need — factor that operational cost in, not just the wire protocol's elegance.
  • Retained messages and the will message are easy to forget about when debugging "why did a stale value show up" — check for a retained flag before assuming a device is actually publishing that value right now.
  • MQTT's persistent TCP connection is exactly the cost CoAP was designed to avoid on genuinely tiny, battery-constrained nodes — MQTT tends to fit better once a device already has a stable network connection to spare.
