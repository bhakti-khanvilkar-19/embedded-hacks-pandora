CoAP — Constrained Application Protocol

An application-layer protocol (RFC 7252) built on top of UDP, designed for small, battery-powered, memory-constrained devices talking over lossy networks. It borrows HTTP's REST model — resources, URIs, GET/POST/PUT/DELETE — but re-encodes everything into a compact binary format and adds its own lightweight reliability on top of UDP's unreliable delivery.

Why not just use HTTP?

HTTP over TCP works fine on constrained devices in principle, but three things make it a poor fit for the smallest nodes: TCP's connection setup and header overhead per request, HTTP's verbose text-based headers, and TCP's requirement to hold open connection state per peer — expensive in RAM on a device that might have only a few KB to spare. CoAP keeps the REST *model* everyone already knows, but drops the transport and encoding that made it heavy.

Message format

Every CoAP message starts with a fixed 4-byte binary header — contrast with an HTTP request line plus headers, which is easily 100+ bytes of text:

FieldSizePurpose
Ver2 bitsProtocol version.
Type2 bitsCON, NON, ACK, or RST (see below).
TKL4 bitsLength of the token that follows (used to match responses to requests).
Code8 bitsMethod (e.g. GET) on a request, status (e.g. 2.05 Content) on a response.
Message ID16 bitsDetects duplicates and pairs ACKs with the message they acknowledge.

After the header: an optional token, a set of TLV-encoded options (the CoAP equivalent of HTTP headers — URI-Path, Content-Format, Observe, etc.), and an optional payload.

Reliability on top of UDP

Raw UDP (see UDP) gives you no delivery guarantee at all. CoAP adds a thin, optional reliability layer using its message type field, without pulling in anything like TCP's connection state:

CON
Confirmable — the sender retransmits (with exponential backoff) until an ACK arrives or retries are exhausted.
NON
Non-confirmable — fire-and-forget, no retransmission; used for data where a missed update doesn't matter (e.g. periodic sensor readings).
ACK
Acknowledges a CON message, and — since CoAP is request/response — usually piggybacks the actual response in the same packet.
RST
Sent when a message can't be processed (e.g. the receiver has no state for it) — tells the sender to stop.

This is deliberately much simpler than TCP's sliding windows and congestion control — CoAP only needs "did the other end get this request/response," not a general-purpose reliable byte stream.

REST semantics: methods and response codes

CoAP requests target a resource identified by a URI path, using the same method vocabulary as HTTP: GET, POST, PUT, DELETE. Response codes reuse HTTP's class structure but pack the class and detail into a single byte, written as class.detail:

CoAP codeMeaningHTTP equivalent
2.05 ContentSuccess, response has a body200 OK
2.01 CreatedResource created201 Created
4.04 Not FoundNo such resource404 Not Found
4.05 Method Not AllowedMethod doesn't apply to this resource405 Method Not Allowed
5.00 Internal Server ErrorServer-side failure500 Internal Server Error

Observe and block-wise transfer

Two extensions matter enough in practice to know by name:

  • Observe (RFC 7641) — a client GETs a resource with an Observe option set, and the server keeps sending updated representations whenever the resource changes, without the client re-requesting. It turns plain request/response into a lightweight publish/subscribe pattern, without needing a broker.
  • Block-wise transfer (RFC 7959) — splits a payload too large for one datagram into a sequence of numbered blocks, since constrained nodes and paths often can't reliably move large single UDP payloads.

When to choose what

Decision guide
  • Choose raw UDP when you control both ends completely, need the absolute minimum overhead, and don't need REST semantics, standardized discovery, or interoperability with anything else — you're willing to hand-roll framing and (if needed) reliability yourself.
  • Choose CoAP when you want REST-style request/response (GET a sensor value, PUT an actuator state) on a constrained device, want optional reliability without TCP's cost, need multicast discovery on a local network, or want interoperability with other CoAP-speaking devices/tools.
  • Choose MQTT when the shape of the problem is really publish/subscribe with many producers and consumers, and a central broker plus TCP's connection overhead is acceptable (i.e. the device isn't as constrained, or already needs a persistent connection anyway).
  • Choose HTTP when the client is a normal web browser or service, constraints don't apply, and you want to use the existing web ecosystem (auth, caching, tooling) as-is.

Pros and cons

ProsCons
Raw UDP Minimal possible overhead; total control; simplest mental model for a fixed, closed system. No standard semantics — you invent framing, addressing, and reliability yourself, and re-invent bugs others already fixed; zero interoperability.
CoAP Small, fast, low-power; REST semantics developers already know; optional reliability; native multicast/discovery; DTLS (CoAPs) or OSCORE for security. Still UDP underneath, so NAT traversal and firewall friendliness are worse than TCP-based options; smaller ecosystem/tooling than HTTP; security is an added layer, not built in by default.

Gotchas

Field notes
  • CON retransmission has its own timeout/backoff — don't also build a duplicate reliability layer above it, or timeouts compound.
  • The Message ID (for dedup/ACK matching) and the Token (for matching a response to its request) are separate mechanisms with separate purposes — conflating them is a common source of confusing bugs when writing a CoAP client from scratch.
  • Plain CoAP is unencrypted, same as plain HTTP — production deployments need DTLS (CoAPs, like UDP's answer to TLS) or OSCORE, not "add it later."
  • Many corporate/carrier firewalls block or heavily rate-limit UDP more aggressively than TCP:443 — a real deployment constraint UDP-based protocols share, CoAP included.
What I learned

CoAP's real trick isn't "REST over UDP" by itself — plenty of things run over UDP. It's putting just enough of TCP's useful behavior (optional reliability, dedup, request/response correlation) back on top of UDP as an application-layer concern, so a constrained device only pays for the guarantees it actually needs on a per-message basis, instead of a connection-wide all-or-nothing guarantee like TCP gives you.
