Domain

Networking

How bytes get from one machine to another — and, just as importantly, how the dozen-odd protocols below stack on top of each other to make that happen. None of them work alone: Ethernet can't reach past your local network, IP can't tell one program on a machine from another, and TCP/UDP don't know or care what's inside the message they're carrying. Each topic is written standalone, but they were designed to be read in the order below the first time through.

How the pieces fit together

Every protocol here sits at one of four layers, each one solving exactly the problem the layer below it can't. Application protocols never talk to Ethernet directly — they hand data down, one layer at a time, and each layer only ever talks to the one immediately above or below it. If you've also heard of a 7-layer model (OSI) and aren't sure how it relates to the 4 layers here, or you've ever wondered why "TCP/IP" doesn't leave UDP out in the cold, OSI vs. TCP/IP Model answers both directly — read it first if either of those has ever tripped you up.

  • Ethernet gets a frame to the next device over — nothing further. It has no idea what "the internet" is.
  • IP solves what Ethernet can't: addressing and routing across many networks, hop by hop, with no delivery guarantee of its own. (BGP is the protocol that actually builds those routing tables at internet scale — it technically runs over TCP, one layer up, even though its job is squarely about this layer.)
  • TCP and UDP solve what IP can't: telling one program on a machine from another (via ports), and — for TCP only — turning IP's best-effort delivery into a reliable, ordered stream. QUIC is a third, newer option here too — reliable like TCP, but built on top of UDP instead.
  • Everything above that is an application protocol — a message format and set of rules built on top of a transport for one specific job. This domain now covers ten of them; see the full grouped list below.

Where to start

If you're new to this domain, read in this order — each topic assumes you already understand the one before it, and explicitly says so where it matters.

  1. OSI vs. TCP/IP Model — read this zeroth, even before Ethernet. It sets up the vocabulary ("Layer 3," "Layer 7") and the layering mental model every other topic here assumes.
  2. Ethernet — every topic above this one exists to solve a problem Ethernet by itself can't.
  3. IP — once you've seen Ethernet's "local only" limit, IP's whole reason for existing (addressing across networks) makes sense.
  4. TCP, then UDP — read TCP first; UDP's own page explains itself largely by contrast with TCP's guarantees. QUIC is worth reading right after both, since it only makes sense as a reaction to specific costs in each.
  5. Pick an application protocol by what you're actually building:
    • Web traffic, general request/response → HTTP, then HTTPS & TLS
    • A persistent connection the server can push to → WebSocket
    • Automatic network configuration for a new device → DHCP
    • Remote shell access or administration → SSH
    • Legacy file transfer → FTP
    • Outbound notification/alert email → SMTP
    • IoT devices publishing to a broker → MQTT
    • Constrained/battery-powered devices, REST-style → CoAP
    • Enterprise messaging with routing rules → AMQP
  6. Then, as reference rather than reading order: BGP (how internet-scale routing tables actually get built), IoT Architecture (how these pieces combine in a real device-to-cloud system), Serialization (how the bytes inside any of these payloads are actually structured), and Linux Networking Tools (how to observe all of the above on a real running system).
