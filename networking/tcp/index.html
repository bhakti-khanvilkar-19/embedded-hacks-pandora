TCP — Transmission Control Protocol

A connection-oriented transport built on top of IP that turns IP's best-effort, unordered packet delivery into a reliable, ordered byte stream — at the cost of connection setup, state, and variable latency.

Quick reference
What it is
A connection-oriented transport that turns IP's unreliable packets into a reliable, ordered byte stream.
Mental model
A phone call: you dial first (handshake), talk in order, and both sides know if the line drops.
Key numbers
3-way handshake before any data flows; minimum 20-byte header; retransmission on unacknowledged segments.
Reach for it when
You need guaranteed, in-order delivery and can accept connection setup cost and variable latency.

Three-way handshake

Before any data flows, both sides synchronize initial sequence numbers:

  1. SYN — client picks an initial sequence number and sends it.
  2. SYN-ACK — server acknowledges the client's SYN and sends its own.
  3. ACK — client acknowledges the server's SYN. Connection is now established.

This is why TCP has connection setup latency that UDP doesn't — at least one full round-trip before the first byte of application data can even be sent.

How reliability actually works

Every byte sent has a sequence number. The receiver sends back acknowledgments (ACKs) naming the next byte it expects. If the sender doesn't see an ACK within a computed retransmission timeout, it resends the unacknowledged data — TCP doesn't require IP to retry anything; it achieves reliability entirely by retransmitting from the endpoints.

Because segments carry sequence numbers, the receiver can also reorder packets that arrived out of order (a normal occurrence when IP routes packets independently) before handing bytes to the application in the correct order.

Flow control and windows

The receiver advertises a window size — how many unacknowledged bytes it's currently willing to buffer — preventing a fast sender from overrunning a slow receiver. Separately, congestion control (e.g. slow start, congestion avoidance) makes the sender ramp up its send rate cautiously and back off sharply on loss, to avoid overwhelming the network path itself rather than just the receiver.

Connection teardown

A graceful close uses a FIN/ACK exchange from each side independently (TCP connections are full-duplex, so each direction closes separately). The side that closes first enters TIME_WAIT for a period to absorb any stray late segments before fully releasing the connection — the reason a server under heavy short-lived-connection churn can accumulate many sockets in that state.

Real-world applications

  • HTTP/HTTPS — essentially all web traffic rides on TCP, which is why a slow connection setup is felt as page-load latency.
  • Firmware-over-the-air (FOTA) updates — reliable, ordered delivery matters enormously for shipping a firmware image — a corrupted or reordered byte can brick a device.
  • SSH/remote device management — interactive terminal sessions to embedded Linux boards depend on TCP's ordering guarantees.
  • MQTT/AMQP — both messaging protocols (see MQTT, AMQP) are built on top of TCP specifically for its reliability.

Gotchas

Field notes
  • TCP is a byte stream, not a message protocol — a single send() call is not guaranteed to correspond to a single recv() on the other end. Applications that need message framing add their own (length prefixes, delimiters).
  • Nagle's algorithm can batch small writes, adding latency for latency-sensitive small-message traffic — TCP_NODELAY disables it when that matters.
  • A "connection" is only a local abstraction: intermediate routers hold no per-connection state at all — see IP.
